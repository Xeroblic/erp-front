# Zentria ERP — v2.3.1

**Fecha de lanzamiento:** 27 de agosto de 2026
**Versión anterior:** v2.3.0

## Resumen

Zentria ERP v2.3.1 fortalece el flujo de **Revisiones Técnicas** y estabiliza comportamientos visibles de catálogo, ventas y autorización. La versión permite declarar la ausencia de RAM o almacenamiento sin perder el borrador del formulario, mejora la seguridad de contratos de estado y hace explicables las acciones que quedan deshabilitadas por autorización.

---

## Funcionalidades y mejoras

### Revisiones técnicas

- Declara la ausencia de RAM y almacenamiento mediante `has_no_ram` y `has_no_storage`, enviando `null` para los campos dependientes cuando corresponde.
- Conserva los valores del formulario al activar y revertir una ausencia antes de guardar.
- Unifica la tarjeta de hardware para notebook, desktop y AIO, con estado colapsado y controles de solo lectura nativamente deshabilitados.
- Alinea los catálogos de RAM y la presentación de AIO con las demás variantes de equipo.

PR relacionados: [#173](https://github.com/Xeroblic/erp-front/pull/173) y [#174](https://github.com/Xeroblic/erp-front/pull/174).

### Catálogo, ventas y autorización

- Valida respuestas parciales de toggles de estado y conserva la entidad local cuando el contrato remoto es inválido.
- Presenta y edita el tipo real de clientes de ventas, sin inferir valores para registros históricos que no lo traen.
- Mantiene visibles las acciones protegidas configuradas como deshabilitadas y explica el bloqueo por mouse y teclado.

PR relacionados: [#170](https://github.com/Xeroblic/erp-front/pull/170), [#171](https://github.com/Xeroblic/erp-front/pull/171) y [#172](https://github.com/Xeroblic/erp-front/pull/172).

### Calidad

- Normaliza configuración de agentes, imports, formato y finales de línea para sostener las puertas de calidad del repositorio.

PR relacionados: #159–#169.

---

## Calidad y compatibilidad

- No se introducen cambios incompatibles conocidos en las interfaces públicas del frontend.
- La ausencia de hardware mantiene el contrato booleano existente con el backend y serializa los campos dependientes como `null` sólo en el payload final.
- La promoción a `main` se verificará mediante el PR de release; este documento no acredita por sí solo un despliegue en producción.

## Deuda conocida no bloqueante

- Queda pendiente un smoke autenticado del auto-guardado de revisiones técnicas y de los fallbacks de autorización en un entorno con credenciales autorizadas.
