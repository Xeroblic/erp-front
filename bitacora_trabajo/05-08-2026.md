## Tema: Roles y permisos: nombres mostrados no usaban `display_name` del backend

**Rama:** `fix/permission-role-display-names`

- **Origen:** en `/gestion/roles-permisos/:id` los permisos mostraban textos armados
  raros que no correspondían a lo enviado por la API.
- **Causa raíz:** el label se generaba 100% en el front con
  `formatPermissionName(permission.name)` / `formatRoleName(role.name)`
  (`src/pages/admin/Permission/utils/formatters.ts`), un traductor slug→español a
  base de diccionarios locales. Cuando el slug no matcheaba los diccionarios caía a
  `toTitleCase` sobre el fragmento crudo. El traductor es **anterior** a que el backend
  enviara `display_name`; cuando el campo apareció el parche se aplicó a medias (solo
  `RoleSelect` e `InvitationsAdmin`, solo para roles, y encima re-procesado).
  La interfaz `Permission` ni siquiera declaraba `display_name`.
- **[fix]** `permissionsSlice.ts`: `Permission` ahora refleja la API real
  (`display_name`, `guard_name`; `code`/`category`/timestamps pasan a opcionales porque
  la API no los envía).
- **[feat]** `formatters.ts`: `resolvePermissionLabel` / `resolveRoleLabel`
  (prefieren `display_name`, `formatXName` queda de fallback legacy) +
  `buildPermissionLabelMap` / `buildRoleLabelMap`.
- **[feat]** `src/hooks/usePermissionLabels.ts`: resuelve el label desde el catálogo del
  store para las vistas que solo reciben el slug (`user.all_permissions`,
  `user.global_roles`, …).
- **[fix]** `RolesTab.tsx`: se quitó el **doble formateo** `formatRoleName(opt.label)`,
  que volvía a pasar el texto del backend por `toTitleCase` y rompía el sentence-case
  y las siglas (ej. "Cobranza SII" → "Cobranza Sii").
- **[style]** Listas de roles/permisos ordenadas por label con `localeCompare(…, 'es')`.
- **Decisión:** el `display_name` del backend NO se re-formatea; es la fuente de verdad.
- **Verificación:** `tsc --noEmit` limpio, `npm run build` OK. Los valores enviados al
  backend siguen siendo los slugs (`option.value`), así que el payload no cambió.
- **Estado:** listo para PR a `develop`.

## Tema: Fix de seguridad: rol super-admin visible en listados asignables

**Rama:** `fix/permission-role-display-names`

- **[fix]** El filtro que oculta el rol super-admin evaluaba
  `normalizeRoleKey(role.display_name || role.name)`. Con el backend enviando
  `display_name: "Super administrador"` eso normaliza a `"superadministrador"`, que no
  coincide con la clave `"superadmin"` → **el rol quedaba asignable para usuarios que no
  son super-admin**. Bug activo, previo a esta rama.
- Afectaba dos puntos: `CreateInvitationModal.tsx` (modal de invitación, en uso) y
  `RoleSelect.tsx` (prop `hideSuperAdmin`, hoy sin consumidores).
- **Solución:** helper `isSuperAdminRole()` en `formatters.ts` que evalúa **siempre el
  slug canónico** (`role.name`), nunca `display_name`.
- **Estado:** corregido en esta rama.
