## Sesión 22:10 – 23:10 · rama `fix/jwt-refresh-session-expiry-1h`

- **[fix]** Inicio de investigación: a los usuarios se les cierra la sesión tras ~1 hora.
  Síntoma observado en consola: `POST /api/refresh` responde **500** y a partir de ahí
  todas las peticiones (`/perfil`, `/user/personalization`, `/products`, etc.) caen en
  **401**, forzando el login.
- **Rama:** creada a partir de `develop` como `fix/jwt-refresh-session-expiry-1h`.
- **Motivo:** el token JWT de acceso expira (~60 min) y el flujo de refresh
  (`BaseService` + `tokenRefreshWorker` + `tokenManager`) no logra renovarlo, cerrando la
  sesión del usuario.
- **Estado:** en investigación. Revisando interceptores de `BaseService.ts`, worker
  proactivo y configuración de TTL/margen.

### Hallazgos (diagnóstico)

- **Causa del 500 (backend, `zentria-erp-back`, solo lectura):** en `bootstrap/app.php`
  solo hay handlers para `AuthenticationException` (401) y `TokenBlacklistedException`
  (401). **No** hay handler para `TokenExpiredException` / `TokenInvalidException` /
  `JWTException`, por lo que `POST /refresh` (`AuthController::refresh` →
  `auth('api')->refresh(false, true)`) renderiza esas excepciones como **500** en vez de
  401. El frontend interpreta el fallo del refresh como sesión perdida → `logout()`.
- **Config tiempos:** backend `JWT_TTL` = 30 min (prod, default) / 1440 (local);
  `refresh_ttl` = 10080 min (7 días); `blacklist_grace_period` = 30 s. Frontend
  `VITE_JWT_REFRESH_TTL_MINUTES=10080` (coincide) y `VITE_JWT_REFRESH_MARGIN_SECONDS=15`
  → el worker fuerza mínimo **30 s** de margen.
- **Factores frontend que agravan:**
  1. **Margen de refresh muy chico (30 s):** si el timer se retrasa (pestaña en segundo
     plano / equipo suspendido / `setTimeout` throttled), el access token expira antes de
     refrescar y se entra al camino reactivo (refresh de token ya vencido) → 500.
  2. **El interceptor reactivo hace `logout()` al PRIMER fallo del refresh**
     (`BaseService.ts:184`), sin reintento ni distinguir 500 transitorio de 401 real.
  3. **No hay sync de token entre pestañas:** `tokenManager` guarda el token solo en
     memoria; el comentario "magia para la Pestaña B" referencia un cross-tab sync que no
     existe → en multipestaña se invalidan tokens mutuamente.
- **Restricción:** el backend es **solo lectura** → el fix definitivo (handlers de
  excepción) hay que recomendarlo al equipo de back; en el front podemos mitigar
  (margen + no cerrar sesión ante fallo transitorio + sync cross-tab).

### Cambios aplicados

- **[fix]** `VITE_JWT_REFRESH_MARGIN_SECONDS`: `15` → `300` en `.env`, `.env.development`
  y `.env.production`. El worker fuerza mín. 30s, así que el margen efectivo sube de 30s
  a 300s: el refresh proactivo ocurre con el token aún válido (~5 min antes de expirar),
  evitando el camino reactivo que produce el 500. Alineado con el ciclo de vida real del
  JWT (renovar antes de `exp`, no después). No se inventa lógica nueva.
- **[fix]** `BaseService.ts` (interceptor de response): el `logout()` ante fallo del
  refresh ahora es **condicional**. Solo se cierra sesión si el refresh devolvió 401/403
  (fallo de auth real) o si `tokenManager.canRefresh()` es `false` (token fuera de la
  ventana de `refresh_ttl`). Un 500/502/503 o error de red ya **no** cierra sesión: se
  rechaza la petición y el worker proactivo reintenta. Se eliminó el comentario engañoso
  de "magia para la Pestaña B" (aludía a un cross-tab sync inexistente). Typecheck OK.
- **[refactor]** Limpieza de `BaseService.ts` (475 → 195 líneas): se eliminó el bloque
  legacy "V1 ANTIGUO" (~280 líneas comentadas), comentarios duplicados y el campo de tipo
  sin uso `_retryWithMemoryToken`. Se tipó la respuesta del refresh (`RefreshTokenResponse`,
  sin `any`), se extrajo `requestNewToken()` y se reemplazó el anti-patrón
  `new Promise(async ...)` por una promesa con `.finally()`. Comportamiento idéntico;
  typecheck y ESLint limpios (solo quedan 2 `import/extensions` preexistentes del repo).
- **Recomendación al equipo de backend (solo lectura):** agregar en `bootstrap/app.php`
  handlers `render` para `TokenExpiredException` y `JWTException` que devuelvan 401 (hoy
  caen en 500).

### Backend — solo lectura (NO modificar). Hallazgos y recomendaciones para el equipo back

  síntoma de "se cierra tras ~1 hora" cuando el refresh proactivo no alcanza a renovar.
- `refresh_ttl` = **10080 min (7 días)** → el front ya usa el mismo valor
  (`VITE_JWT_REFRESH_TTL_MINUTES=10080`).
- `blacklist_enabled` = **true**; `blacklist_grace_period` = **30 s** (mitiga fallos por
  requests concurrentes que reusan el mismo token durante ese margen).
- `leeway` = **0** → sin tolerancia a desfase de reloj cliente/servidor; un reloj
  adelantado en el cliente puede dar `exp`/`nbf` inválidos.

2. **Evaluar `leeway`** > 0 (p. ej. 30–60 s) si se detecta desfase de reloj en clientes.
3. (Opcional) Revisar si conviene un `ttl` mayor en prod para reducir frecuencia de
